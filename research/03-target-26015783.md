## 좌석 화면 API (2026-11-16, 사용자 HAR `tickets.interpark.com.har` 2차 — 전 좌석 매진 상태)

요청 순서: `GetSeatGradePrices` → `VerifyCaptcha`(보안문자, 내용 열람 안 함) → `seatMeta` ×15 → `seatStatus` 반복

### `GET tickets.interpark.com/onestop/api/seatMeta?goodsCode&placeCode&playSeq&blockKeys=…&blockKeys=…&bizCode`
- `blockKeys`는 **여러 번 반복되는 쿼리 파라미터**. 형식 `{playSeq}:{구역번호}` (예 `001:001`~`001:007` FLOOR, `001:101`~`001:110` 1층, `001:223`~`001:235` 2층 일부)
- 응답 `{data: [{blockKey, seats: [...]}]}`. 구역당 약 200~420석, 이번 기록에서 30개 구역 8,310석
- 좌석 필드: `seatInfoId`(`{goodsCode}:{placeCode}:{playSeq}:{번호}`), `seatGrade`, `seatGradeName`, `floor`("FLOOR"/"1층"…), `rowNo`(예 "A구역 10열", "9구역 12열", 빈 문자열도 있음), `seatNo`, `salesPrice`, `seatGroupId`, `posLeft`, `posTop`, `rowIdx`, `colIdx`, `isExposable`(false 1,181석)
- 배열 순서는 `seatInfoId` 번호 오름차순 (rowIdx/colIdx 순 아님)
- 크기가 커서(구역당 100~200KB) 처음 한 번만 받는 것으로 보임

### `GET tickets.interpark.com/onestop/api/seatStatus?…(같은 쿼리)`
- 응답 `{data: ["0000…", ...]}` — `blockKeys` 순서대로 구역마다 문자열 하나
- **문자열 길이 = ceil(구역 좌석 수 / 4)** (224→56, 287→72, 377→95, 418→105, 304→76). 137개 구역-응답 쌍 모두 일치
  - → **16진수 한 자리가 좌석 4개를 비트로 표현하는 비트맵**으로 추정. 좌석 순서는 seatMeta 순서(isExposable false 포함 전체)
  - 관찰 시점 전부 `0` = 전 좌석 매진과 일치
  - **미확인**: 비트 1이 "예매 가능"인지, 자리 안에서 비트 순서(상위 비트부터인지)
- **갱신**: 같은 구역 묶음이 조작 없이 약 3.3초 간격으로 다시 요청됨 (2.5s, 5.7s, 9.1s). 기록이 9초뿐이라 주기적 갱신인지 확정 필요
  - 주기적 갱신이 맞으면: **확장은 응답을 읽기만 하면 되고 자동 새로고침(DESIGN 9)이 필요 없다**

### 남은 확인 (빈 좌석이 있는 공연으로 확인 가능)
1. 비트 의미와 순서: 빈 좌석이 있는 아무 공연의 좌석 화면에서 HAR을 뜨고, 화면에 보이는 빈 좌석 위치와 비트를 대조
2. 갱신 주기: 좌석 화면에서 조작 없이 1~2분 기록

### 비트 순서 — 확정: 16진수 한 자리 안에서 상위 비트부터
| 기준 | 상위 비트부터 | 하위 비트부터 |

### 비트 의미 — 1 = 예매 가능 (근거 두 가지)
1. 전석 매진인 성시경 공연은 모든 비트 0
2. 판매 불가인 비노출 좌석은 항상 0
- 이 공연 B구역: 95석 중 74석 예매 가능, A·C구역 전부 0

### 해석 규칙
```
seats = seatMeta[blockKey].seats              // seatInfoId 오름차순, 비노출 포함 전체
bits  = seatStatus 문자열의 각 16진수 자리를 상위 비트부터 4비트씩 펼침
seats[i] 예매 가능 ⇔ bits[i] === 1            // 남는 비트(패딩)는 0
```
