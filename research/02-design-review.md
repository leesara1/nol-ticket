# 설계 검토 결과

초기 설계(화면 감시 + Playwright CDP 연결 + 예매자 정보 자동입력)를 검토한 결과입니다. NOL 내부 구조에 대한 내용은 사전 조사로 확인해야 하는 가설입니다.

## 핵심 발견: 좌석맵은 저절로 바뀌지 않을 수 있음

예매 사이트 좌석맵은 보통 불러온 시점의 모습에 머뭅니다. 그렇다면 기존 `nol_screen_alert.py`(화면 픽셀 비교)는 화면이 변하지 않으므로 아무것도 감지하지 못합니다.

→ 사전 조사 첫 질문: **좌석맵을 열어두면 저절로 갱신되는가?** (1시간 관찰, DevTools Network에서 주기적 XHR/WebSocket 확인)
- 갱신된다 → 관찰만으로 충분. 자동 새로고침 불필요
- 갱신 안 된다 → 새로고침이 필요하며, 이것이 약관상 가장 민감한 부분

## 권고와 반영 여부

| # | 권고 | 근거 | 반영 |
|---|---|---|---|
| 1 | 페이지가 이미 받은 네트워크 응답에서 좌석 읽기 | 좌석 ID·등급·구역·열 정보가 정확. 캔버스 좌석맵에서도 동작. 추가 요청 0 | ✅ FR-1 1순위 |
| 2 | Playwright CDP 대신 크롬 MV3 확장 | 크롬 136부터 기본 프로필에서 `--remote-debugging-port` 무시됨. 확장이 탭 제어·알림을 기본 제공. 단, Windows 포그라운드 잠금은 확장도 피하지 못함 → `drawAttention` + 알림 클릭 시 포커스로 보완 (DESIGN 11.1) | ✅ 구조 변경 |
| 3 | 잔여석 수 먼저 감시하는 2단계 구조 | 좌석맵 반복 새로고침보다 가벼움 | ⚠️ 대상 공연은 `잔여석 숨김`이라 적용 어려움 |
| 4 | 취소표가 풀리는 시간대에 집중 | 같은 요청 수로 더 잘 잡음 | ✅ FR-7 시간대 제한 |
| 5 | 감시 불능 상태 감지 + 생존 신호 | 조용한 실패가 가장 흔한 실패 유형 | ✅ FR-11, FR-12 |
| 6 | 구조화된 데이터는 2회 확인 생략 | 30~60초 손해 | ✅ FR-5 |
| 7 | 예매자 정보 자동입력 축소, DPAPI/keyring 제거 | NOL이 계정 정보로 미리 채울 가능성 큼 | ✅ FR-15 (빈 칸만, 필요 시) |
| 8 | 알림 지연 순위: 탭 소리·크롬 알림(<100ms) > 텔레그램(1~3초) | 병목은 새로고침 간격과 사람 반응 | ✅ FR-10 동시 발송 |
| 9 | OS 접근성(UI Automation) 사용 안 함 | 크롬 접근성 트리 불완전, 캔버스는 정보 없음 | ✅ 제외 |
| 10 | 새로고침 간격에 무작위 지연 추가 | "기계처럼 보이지 않게" | ⛔ **채택 안 함.** 봇 탐지 회피에 해당 |
| 11 | 과설계 피하기: 플러그인 레지스트리 없이 어댑터 2~3개 | 단순성 | ✅ |

## 기타 메모

- 백그라운드 탭 타이머는 크롬이 제한함(숨김 5분 후 약 1분에 1회) → `chrome.alarms` 사용 (MV3 최소 30초)
- 대기열 화면이 나오면 자동 새로고침 중단 후 알림. 대기열 자동 통과 금지
- 별도의 keep-alive 요청은 두지 않음. 새로고침 자체가 세션 유지 역할
- MV3 `webRequest`로는 응답 본문을 읽을 수 없음 → MAIN world 스크립트로 페이지의 fetch/XHR 응답을 **읽기만** 함
